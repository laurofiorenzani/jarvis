# JARVIS Family CFO — data and capability contract

Status: design contract only; no Family CFO tables, bank connectors, financial imports, balances, or money-moving tools are implemented by this document.

## 1. Purpose and non-goals

Family CFO provides an auditable household financial picture: income, spending, budgets, cash flow, savings, debt, mortgage, pensions, investments, property, insurance, and scenario planning. It must distinguish imported facts from user-entered assumptions and calculated projections.

The first release is **read-only and analysis-only**. It may classify, reconcile, summarize, forecast, and prepare recommendations. It must not initiate transfers, payments, trades, account changes, credit applications, or external messages. Any future action capability requires a separately designed approval flow, explicit per-action consent, idempotency, and audit trail.

## 2. Identity, household consent, and isolation

- Supabase Auth user ID is the security principal for every record.
- Lauro and Isabelle remain separate accounts. No implicit shared access, shared credentials, or cross-account queries.
- Household aggregation is a separate opt-in sharing relationship, not a side effect of marriage, a shared device, or a common address.
- Each participant must explicitly consent to each category of data they share (accounts, income, debts, assets, pension, property, documents).
- A user can revoke sharing; revocation must stop future access and invalidate cached household aggregates.
- Service-role access stays server-side. RLS policies scope personal rows to the owner and household-shared rows to a currently active, consented membership.
- Do not use financial data for model training or send it to an external provider unless the account holder has accepted a clear provider/data-transfer notice and that provider is eligible under the project's zero-cost and privacy policy.

## 3. Canonical record envelope

Every imported or user-entered financial fact must carry:

| Field | Requirement |
|---|---|
| `id` | UUID generated by the backend |
| `owner_user_id` | Authenticated owner |
| `household_id` | Nullable; populated only after explicit sharing |
| `source_type` | `manual`, `bank_export`, `provider_api`, `document`, `calculation` |
| `source_name` | Institution, file, connector, or calculation identifier |
| `source_record_id` | Nullable external ID for deduplication |
| `observed_at` | When the source data was observed |
| `effective_at` | Date the financial event/value applies to |
| `imported_at` | Server import timestamp |
| `currency` | ISO 4217 currency code |
| `confidence` | `verified`, `user_confirmed`, `estimated`, `unknown` |
| `status` | `pending_review`, `confirmed`, `rejected`, `superseded` |
| `provenance` | Safe source locator, checksum, and import method; never raw credentials |

Money values must use exact decimal/numeric representation, never binary floating-point. Preserve the original currency and amount. Convert currencies only into a separate derived value with the exchange-rate source, rate, timestamp, and calculation method attached.

## 4. Core domain entities

### Accounts and balances
- Financial institution/account label, account type, masked identifier, owner, currency, and connection/import state.
- Balance snapshots are timestamped observations, not mutable current truth.
- A stale balance must be labelled stale and must not silently appear as current.

### Transactions
- Posted date, transaction date, signed amount, currency, merchant/counterparty, original description, category, account, pending/posted/reversed status, and source reference.
- Preserve original bank text. Categorization is a separate model/user annotation with confidence and review status.
- Deduplicate using institution ID when available; otherwise use a conservative fingerprint and retain collision review.
- Transfers between owned accounts must be paired and excluded from household income/expense totals when confidently matched.

### Income, budgets, and recurring commitments
- Income sources, gross/net distinction, frequency, effective dates, and evidence.
- Budgets are user-defined targets with period, category, currency, and owner.
- Recurring commitments are estimates until confirmed against actual transactions; never synthesize a paid transaction from a recurring rule.

### Liabilities and mortgage
- Principal balance, interest rate/type, rate effective dates, term, payment schedule, fees, lender, and source date.
- Separate principal, interest, fees, overpayments, and escrow/insurance where present.
- Mortgage payoff scenarios must disclose assumptions (rate, payment, overpayment timing, fees, compounding, and recalculation rules). Do not claim a lender-approved payoff figure.

### Assets, property, pensions, and investments
- Asset valuation is a dated estimate with source and valuation method; do not treat asking prices as completed-sale evidence.
- Pension balances and contributions retain scheme, employee/employer/AVC split, fees, projected assumptions, and statement date.
- Investment holdings retain instrument identifier, units, price source, timestamp, currency, and fees. Projections are scenarios, not guaranteed returns.
- Net worth is a derived snapshot: confirmed assets minus confirmed liabilities, with estimated values visibly separated.

### Documents and evidence
- Store document metadata and access-controlled object references; avoid duplicating raw documents into logs or model prompts.
- Extracted facts remain pending until a user confirms them, unless the user explicitly opts into a documented automatic-import category.
- Keep a reference to the source page/row and extraction confidence for audit.

## 5. Source and connector policy

- Prefer official provider APIs or user-authorized exports (CSV, OFX, PDF statements). Never request passwords, card numbers, full account numbers, PINs, or one-time codes in chat.
- A connector must document scopes, data coverage, refresh behavior, rate limits, regional processing, retention, revocation, and free-tier/billing constraints before activation.
- If an API is unavailable, use an explicit user-uploaded statement/export flow; do not scrape a banking website or bypass MFA.
- Imported data is not assumed complete. Each report must show source coverage, last refresh, missing accounts/periods, and pending records.
- Do not assume Revolut, AIB, Irish Life, mortgage lenders, Revenue, or investment providers have usable free APIs; verify each provider's current official capabilities before implementation.

## 6. Analytics and reporting contract

Every dashboard/report must show:
1. Reporting period and currency.
2. Sources included and last refresh time.
3. Confirmed vs estimated vs pending values.
4. Missing data and known coverage gaps.
5. Calculation formula and assumptions for derived metrics.
6. Whether a value is nominal, inflation-adjusted, gross, or net.

Supported first-release calculations:
- Cash flow: confirmed inflows minus confirmed outflows, excluding internal transfers.
- Spending: posted transactions only, with uncategorized totals visible.
- Savings rate: clearly defined numerator/denominator and gross/net basis.
- Debt trajectory: scenario projection from a dated principal balance and explicit assumptions.
- Net worth: dated asset/liability snapshot with confidence labels.
- Pension and retirement: scenario ranges with contributions, fees, inflation, tax and return assumptions exposed.

No invented balances, transactions, interest rates, tax rules, market prices, or property values. If inputs are missing, show the gap and ask for the smallest required source.

## 7. Suggested logical schema (not yet migrated)

- `cfo_households`: household identity and lifecycle.
- `cfo_household_members`: user membership, role, invitation/acceptance, and revocation.
- `cfo_data_consents`: per-user, per-category sharing/provider consent with version and timestamps.
- `cfo_accounts`: institution/account metadata and masked identifiers.
- `cfo_balance_snapshots`: timestamped balance observations.
- `cfo_transactions`: source-backed transaction records and review state.
- `cfo_categories`, `cfo_transaction_classifications`: canonical categories and versioned classifications.
- `cfo_income_sources`, `cfo_budgets`, `cfo_recurring_items`.
- `cfo_liabilities`, `cfo_mortgage_terms`, `cfo_debt_snapshots`.
- `cfo_assets`, `cfo_valuations`, `cfo_pension_snapshots`, `cfo_investment_positions`.
- `cfo_documents`, `cfo_import_runs`, `cfo_reconciliation_events`.
- `cfo_scenarios`, `cfo_reports`, `cfo_audit_events`.

Do not create these tables until the schema, indexes, RLS policies, retention/deletion behavior, consent revocation, and two-account isolation tests are reviewed together. Do not add permissive client policies to silence security lint.

## 8. Zero-cost, security, and reliability gates

- No paid APIs, subscriptions, per-token billing, paid connector tiers, or automatic upgrades.
- Provider eligibility requires verified free quota, zero-spend controls, region eligibility, retention/training terms, and per-user consent. Unknown means disabled.
- No provider key, bank credential, account identifier, transaction description, or document content in logs.
- Encrypt sensitive source artifacts at rest; define key ownership, backup, restore, export, deletion, and retention before importing real financial records.
- Enforce request size, import row count, file size, parser time, API calls, retries, and storage quotas.
- Maintain an auditable import ledger; repeated import must be idempotent.
- Financial calculations require deterministic tests for rounding, time zones, negative balances, reversals, transfers, duplicate imports, stale values, and FX rates.
- Require two-account RLS tests, household consent/revocation tests, and restore tests before production data ingestion.

## 10. Acceptance criteria

- Every displayed fact is traceable to a source and timestamp.
- No stale or estimated figure is presented as verified current data.
- Re-importing a source does not duplicate transactions.
- Internal transfers do not inflate income or spending.
- Each account is isolated by default; household views require explicit bilateral consent.
- All money values use exact decimal arithmetic and retain source currency.
- Reports expose assumptions and missing data.
- No financial action can be executed by the analysis-only release.
- The feature operates within the project's €0 recurring-cost policy.
